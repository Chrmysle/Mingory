# Mingory 导航与 UI 重构方案

## 1. 当前页面结构

当前小程序共有 15 个页面，全部通过普通页面栈访问，没有一级 TabBar：

- `pages/index`：身份状态、今日经营、扫码、商品、销售记录、进货助手入口混合在同一页。
- `pages/product-list`、`product-search`、`product-create`、`product-detail`、`product-edit`：商品模块。
- `pages/sale`、`sales`、`sale-detail`：销售执行和历史记录。
- `pages/stock-in`、`stock-adjust`、`inventory-logs`：库存操作与流水。
- `pages/restock-suppliers`、`restock-items`：按供货商补货。
- `pages/business-statistics`：经营统计。

现有公共层包括 `services`、`utils`、数据模型以及一个 `suggestion-input` 组件。Product + Variant、销售事务、库存事务、白名单和幂等机制已经稳定。

## 2. 当前存在的问题

- 一级业务边界不清晰，首页同时承担状态、经营、销售、商品、库存导航。
- 高频“卖货”没有独立工作区，扫码和销售记录分散在首页及二级页。
- 库存操作只能从商品详情逐层进入，补货、流水和盘点缺少统一入口。
- 统计页只有摘要，信息层级与其他普通表单页接近，缺少数据阅读节奏。
- 当前浅色视觉对数据层级表达有限；列表、指标、状态和操作的对比还不够统一。
- 页面已有重复的标题、空状态、分段筛选和数据行样式，但暂未形成轻量公共规范。

## 3. 新 TabBar 结构

使用微信原生 TabBar，不实现自定义 TabBar：

1. 首页：`pages/index/index`
2. 卖货：`pages/sell/index`
3. 商品：`pages/product-list/index`
4. 库存：`pages/inventory/index`
5. 统计：`pages/business-statistics/index`

原生 TabBar 保留平台熟悉的切换行为、稳定点击区域和页面状态，不用视觉自由度换取额外维护成本。

## 4. 每个 Tab 的职责

### 首页

回答“今天店里现在是什么状态”：今日经营、四个高频入口、最紧急库存提醒、最近销售。只展示摘要。

### 卖货

回答“如何最快完成一笔销售”：扫码卖货、搜索商品、最近售出商品和销售记录入口。销售确认仍复用 `pages/sale`。

### 商品

回答“店里有什么商品”：搜索、扫码、新增、分页商品列表和商品详情入口。

### 库存

回答“什么缺货、为什么变化、去哪里进货”：缺货/低库存摘要、进货助手、盘点入口、进货记录、库存流水和紧急 SKU。

### 统计

回答“这段时间经营得怎么样”：时间范围、营业额、成本、毛利润、销售数量、记录数以及销售明细入口。数据按概览到明细逐层组织。

## 5. 原页面迁移关系

| 原入口/页面 | 新位置 | 处理方式 |
| --- | --- | --- |
| 首页商品/销售/库存菜单 | 五个 Tab 和各 Tab 内快捷入口 | 移除首页堆叠菜单 |
| `product-list` | 商品 Tab | 保留数据逻辑，升级为一级页面 |
| `business-statistics` | 统计 Tab | 保留统计逻辑，升级为一级页面 |
| `sale` | 卖货二级页 | 保留 |
| `sales` / `sale-detail` | 卖货 → 销售记录 → 销售详情 | 保留 |
| `product-create/search/detail/edit` | 商品 Tab 下二级页面 | 保留 |
| `stock-in/stock-adjust/inventory-logs` | 库存 Tab 或商品详情下二级页面 | 保留 |
| `restock-suppliers/restock-items` | 库存 → 进货助手 → 供货商详情 | 保留 |

## 6. 新增页面

- `pages/sell`：卖货一级工作区。
- `pages/inventory`：库存一级管理中心。

不新增商品、销售、库存数据库模型。全局库存流水和进货记录复用 `inventory_logs` 查询能力。

## 7. 删除或废弃

- 不删除任何已完成业务页面。
- 废弃首页原有的完整功能菜单入口；入口迁移到对应 Tab。
- 不再把统计页和商品列表当作普通二级入口跳转，它们成为原生 Tab 页面。

## 8. 页面导航关系

```text
Tab 首页
├─ 扫码卖货 → 销售确认
├─ 搜索商品 → 商品搜索 → 商品详情
├─ 新增商品 → 新增商品
└─ 进货补货 → 进货助手 → 供货商补货详情 → 入库

Tab 卖货
├─ 扫码卖货 → 销售确认
├─ 搜索结果 → 单规格直接销售 / 多规格商品详情
└─ 销售记录 → 销售详情

Tab 商品
├─ 搜索商品 → 商品详情
├─ 扫码查商品 → 商品详情
├─ 新增商品
└─ 商品详情 → 编辑 / 销售 / 入库 / 调整 / 库存记录

Tab 库存
├─ 进货助手 → 供货商补货详情 → 入库
├─ 选择商品盘点 → 商品详情 → 库存调整
├─ 进货记录
└─ 库存流水

Tab 统计
└─ 销售明细 → 销售记录 → 销售详情
```

一级页面使用 `switchTab` 或原生 TabBar；二级业务页面继续使用 `navigateTo`。

## 9. 完全不需要修改的业务代码

- Product + ProductVariant 数据结构。
- `createProduct`、`updateProduct`、`getProduct`、`searchProducts` 的商品规则。
- `saleProduct` 的事务、成本快照、扣库存和 requestId 幂等。
- `stockIn`、`adjustStock` 的事务与 `inventory_logs` 写入。
- 金额整数分、北京时间范围、用户白名单。
- supplier、warningStock 和补货判定规则。

只允许扩展只读查询结果和页面入口，不改变任何写入规则。

## 10. 实施顺序

1. 配置原生五栏 TabBar，建立卖货和库存一级页面。
2. 迁移旧入口并统一 `switchTab` / `navigateTo` 规则。
3. 重构首页为今日摘要。
4. 重构卖货工作区和商品 Tab。
5. 重构库存中心，复用进货助手、入库、盘点、库存流水。
6. 重构统计页的信息分区和明细入口；图表只在数据源可靠且无需重型依赖时加入。
7. 统一深色 Design Tokens、排版、间距、按钮、表单、状态色与空状态。
8. 仅保留按压反馈和销售/入库成功反馈；不为高频列表增加入场动画。
9. 执行页面路径、JSON、语法、云函数和 Phase 4～6 回归测试。

## 视觉原则

- 深灰背景而非纯黑，Surface 用亮度和轻边框分层，不堆叠阴影。
- Accent 只用于主操作；绿色表示正向利润，红色表示缺货/负利润，橙色表示低库存。
- 大金额使用紧凑行高和略收紧字距；正文保持父母可读尺寸和至少 88rpx 的主要触控高度。
- 借鉴参考图“概览 → 深入 → 明细”的统计阅读顺序，不复制记账分类、品牌、配色或装饰图表。
